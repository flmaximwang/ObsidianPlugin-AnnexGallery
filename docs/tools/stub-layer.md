# 桩层：不启动 Obsidian 也能判的东西

最便宜的一层：用一份最小的 `obsidian` 模块替身把**构建产物** `main.js` 加载起来，直接检查它
注册了什么、渲染了什么、算出什么。目的不是「模拟 Obsidian」，而是把「插件能不能加载、
入口形状对不对、状态栏数字口径对不对」这类问题在不打开 app 的前提下判死。

## `obsidian-stub.cjs` 的边界

它是一份**替身**，不是模拟器。原则：

- 只实现被判据用到的那部分 API（`Plugin` / `ItemView` / `Setting` / `Menu` / `Notice` /
  `addStatusBarItem` / `registerInterval` …），每个实现都尽量薄。
- 实现的语义要跟真机一致到「断言能成立」的程度：例如 `setInterval` 记录毫秒数、
  `walk()` 能遍历出 DOM 树、`Menu` 记录项的顺序与图标。
- **它量不出的东西就别断言**：原生控件的真实宽度、真实 `app.css` 的层叠、外部应用的进程行为，
  这些在桩里要么是常量、要么不存在 —— 硬断言只会得到假答案（对应项在真机层判）。
- 桩只被工具引用，不进构建产物：`main.js` 里的 `obsidian` 始终是那个 external 的 `obsidian`。

## `smoke-test.cjs`：加载与入口形状

- 加载 `npm run build` 的产物、跑 `onload()`，断言插件能启用、清理得干净。
- 断言入口的**形状**：9 个右键菜单项的顺序与图标（第 3 项「创建画廊」的标题随界面语言变）、
  顶层项只 `preventDefault`、右键文件不出现选项、设置页渲染出的字段（含 remote 区、文件名匹配模板区、
  模板区）。
- 断言**外部文件模型**的行为：三类模板的登记 / 从预设创建 / 打开 / 取消登记；路径越界、扩展名不对、
  文件不存在、重复登记都只弹 Notice；profile JSON 的数组、`{ profiles: [...] }`、坏 JSON、坏正则、
  文件丢失、跨文件 id 重复都在行上可见；运行时重新读外部文件、坏文件在写盘前停下；旧内联 profiles
  只提示不迁移。
- 断言 `styles.css` 里**规则级别的约定**（选择器是否存在、是否用了变量），而不是量几何。
- 判据原则：能写成「顺序 / 存在性 / 计数」的断言就不要写成「等于某个像素值」。

## `layout-check.cjs`：真实 `app.css` 下的离屏几何

- 与桩层的分工：这里加载**真实的 `app.css`**（从本机 Obsidian 安装目录读，只在内存里用），
  在 headless Chromium 里把设置页渲染出来，量 computed style 与盒子。
- 能判：标题与卡片的左边缘是否对齐、工具条的伸缩规则是否生效、分割线的上/下留白是否对称、
  变量（`--size-*` / `--text-*`）是否被正确引用。
- 判不了：原生 `<select>` 按最长选项文字定宽（离屏时 option 没有文字）、外部应用实际打开哪个
  文件、观感是否舒服 —— 这三类归真机层。

## 判据怎么读

两层都以 `PASS / FAIL` 计数 + 成功标记收尾；失败信息里带上实测值与期望值，不写本机路径。
新增一条断言时先问：**它会不会在实现坏掉时真的红？** 不会的话，它属于文档不属于判据。
